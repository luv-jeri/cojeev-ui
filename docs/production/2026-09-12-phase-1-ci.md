## Scoped change

The `npm run gate` workflow step now sets `COJEEV_DOCS_SHARDS: '3'`. The existing production runner already accepts one to three workers, distributes component IDs by position modulo worker count, starts the documentation children concurrently and aggregates their reports before motion verification. Each real documentation child requests its own static preview server on an ephemeral loopback port.

The 90-minute job limit, all subsequent release checks, failure behavior, exact-once coverage, fresh-evidence checks, source-provenance assertions, release artifacts, deployment jobs and production approval gate are unchanged. No production runner architecture or application code changed.

is forced outright for a push to main, a manual dispatch and every pull request into main. The allowlist is
exact-match except for the two shaped rules (`docs/**/*.md` and root `tests/*.test.{mjs,ts}`), so

Suite commands, all reusing existing entry points: **prose** is `git diff --check`, with no dependency
installation; **quick** is `npm run lint`, `npx next typegen && npm run typecheck`, `npm test`,
`npm run reporting:test`, `npm run registry-host:test`; **ci-contract** needs no command of its own, because
`npm test` already globs `tests/*.test.mjs` and so runs both `tests/ci-scope.test.mjs` and the real partition

**analytics-browser** adds the same three intercepted-provider configurations the release job runs

`scripts/run-install-verification.mjs`,
a small runner that serves the freshly built `out/` on an ephemeral loopback port, installs into a fresh

### Release acceptance cannot be reached by a scoped check

1. `.github/workflows/verify.yml` guards the `verify` job with `github.event_name != 'pull_request' || github.base_ref == 'main'`, conditions that read no output of the classifier. A push to main, a manual dispatch and any pull request into main run the complete job whatever the classifier says.
2. The guard also carries `!cancelled() && needs.scope.result != 'success'`, so a scope job that fails runs the full job rather than skipping every job and leaving a pull request unverified, while a run the user cancelled stays cancelled instead of starting a 90-minute release job. Only the two known reduced scopes are excluded from it, so a blank or unrecognised output reaches the full job; `checkpoint` matches `docs` and `checkpoint` explicitly rather than testing `!= 'full'`, which a blank output would have satisfied while every suite flag was false. `scripts/ci-scope.mjs` traps its own errors and still publishes a complete output set saying `scope=full`.
3. The `checkpoint` job builds no release pair, runs no catalogue gate, and uploads `checkpoint-evidence-<sha>`. Only `verify` uploads `release-<sha>`; `beta` and `production` still declare `needs: verify`, still download that artifact and still verify `needs.verify.outputs.*` digests. Their conditions, artifact names and deployment steps are unchanged.
4. The `checkpoint` job's final step always runs and records the pull request head SHA, the tested merge SHA, the selected and omitted suites, and the words "checkpoint only, not release acceptance". Nothing omitted is reported as passing.
5. Only pull request runs supersede an outdated run: `cancel-in-progress` on `verify` is now `${{ github.event_name == 'pull_request' }}`, so a main release run is no longer cancelled by the next push. The scoped job is bounded at 20 minutes; the release budget stays 90.

No branch protection was changed. The required check for release acceptance remains `Verify release`, which
this split leaves running on exactly the events that matter. Because the classifier is read from the pull
request's own checkout, a branch could in principle edit both it and its tests together; that is inherent to
in-repo CI configuration and is contained by rule 1 — the promotion into main always runs the full job.
