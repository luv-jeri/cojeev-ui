# Documentation browser verification

This is a bounded docs audit of **66 base components and four helpers**, not acceptance of one-to-one reference fidelity. Reference-versus-port geometry, CSS, and real animation comparison remain the root fidelity gate. No source defect is inferred solely from a docs composition issue.

## Executed scope

- The settled full pass visited all 70 pages sequentially at **360, 768, and 1440 pixels in light and dark themes: 420 cases**. It captured each first live preview, recorded document overflow and runtime/console errors, and checked the count of all **205 source variant/size combinations**. Desktop/light also has full-page captures. Screenshots do not prove every scrolled variant was visually judged.
- Every entry's shared Preview was tested with actual clipboard content, pointer copy/Preview tab, and keyboard Code tab.
- Component-specific behavior was exercised on the default example at 1440/light: **54 passed, 15 passive entries had no component-owned control, one native-select result is limited**. The table records the actual behavior, including entries with only a relevant keyboard action rather than falsely claiming identical pointer/keyboard coverage.
- Fourteen critical components also passed pointer/keyboard behavior at 360/dark: `accordion`, `carousel`, `data-table`, `dialog`, `dropzone`, `field`, `input`, `input-group`, `input-otp`, `pagination`, `questionnaire`, `sidebar`, `stepper`, `textarea`. This occurred before the later authored InputGroup mobile CSS change; that change is called out below.
- All 70 mobile/light first-preview screenshots were visually reviewed through contact sheets from the first full pass. All 70 settled mobile/dark first-preview screenshots were subsequently reviewed through seven contact sheets. Selected desktop/tablet screenshots and corrected pages were inspected separately. This is not an accessibility certification or an all-state visual verdict.
- No user Chrome session was accessed. All browsers were isolated Playwright Chromium contexts against the local main development server. No upload, publication, external communication, or full reference gate was performed. Dropzone files stayed local.

## Result and limitations

The settled matrix had **418/420 document-bound cases pass**, with **zero console/runtime errors**. The two failures were the same DropdownMenu API heading overflowing by two pixels at 360px in both themes. After its wrapping fix, a targeted six-case rerun passed. Every page's shared Preview copy/code test passed.

The full pass's last chrome navigation exceeded the harness's six-second load timeout. The harness now waits for DOM readiness with a 60-second navigation budget. The first focused run then exposed a pre-hydration filter assertion. A chrome-only confirmation passed five contexts; its remaining 768/dark early tab click was rerun after waiting for the existing Flow mount marker and passed. Taken together, all six contexts have direct passing chrome evidence. These harness timing failures are retained in the JSON rather than counted as product defects.

NativeSelect's native selection API updates the real displayed callback receipt. Headless macOS Chromium does not change its native picker selection with ArrowDown/Enter in this run; the same sequence on a new, bare unstyled select also leaves its value unchanged. Native picker keyboard behavior is **unverified**, not counted as a component pass or failure.

The script uses a small empty-name heuristic, not an accessibility tree audit. Its only full-pass hit was Dropzone's deliberate aria-hidden, tabindex=-1 file input; the visible accessible trigger and real file callback were tested.
